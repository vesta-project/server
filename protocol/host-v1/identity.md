# Host identity, claim and link

All routes below have prefix `/v1/host`. Common encodings and errors are in README.md. Authority is host-owned; no worker can mint owners, host sessions, devices or recovery credentials.

## Records and policy

Account key `accountId` is verified Minecraft Java profile UUID, not display name, email, Xbox name or arbitrary Microsoft `sub`. Device is `{deviceId,accountId,name,ed25519PublicKey,revokedAt}`; a device belongs to one account and is never silently reassigned. Accounts hold primary-owner/owner authority or server grants. Owners see all future servers dynamically. Exactly one primary owner after claim; other owners cannot demote/revoke that account or its devices. Transfer and local recovery are audited transactions. Local recovery requires OS administrator peer credentials on a separate socket/named pipe inaccessible to game and worker accounts; not a loopback HTTP route. Recovery offers revoke-all, increments generation and does not rotate the TLS certificate implicitly. Offline local recovery may replace a device key only for an account already verified and recorded on this host; enrolling a new account still requires fresh online profile proof.

| Role | Allowed scope |
|---|---|
| Primary owner | All host and server actions, owner management and transfer. |
| Owner | All ordinary host/server actions including devices, storage and import; no owner changes/transfer/primary-account revocation. |
| Server admin | Lifecycle, raw console, files, content/packs, backups, players and server settings; no host filesystem browsing, Java executable paths, host roles, recovery, update or worker-link secrets. Server role grants only at/below own authority. |
| Server moderator | Read console, restart, typed kick/ban/whitelist actions; no raw console, files, operator grants, arbitrary scheduling or configuration. |
| Server player | Pack sync and wake; public status only unless separately granted. |

Do not reuse current Administrator capability set unchanged: narrow identity/security/credential capabilities to server scope and exclude indirect raw-command paths for moderators. Promotion to Admin must explain that mods/plugins execute code; if an OS lacks isolation, disclose cross-server effects before confirmation. Linux acceptance must isolate worker/game accounts from host keys and privileged local control.

Host `authGeneration` starts at "1", increases transactionally on every grant/revoke, device/account disable, ownership change or recovery, never wraps/resets. Bearers identify account/device, not fixed roles. Every handler resolves current authority. Sessions are random 32-byte opaque tokens, stored as domain-separated hashes in memory, maximum 15min using wall and monotonic deadlines; no refresh token. Restart invalidates all bearers/challenges/PAKE exchanges, not device records or generation. Existing linked devices can obtain new sessions offline using signatures and pins. New claim/sign-in/link/invite enrollment requires online account verification; outage gives 503 `account_verification_unavailable`, never cached verification to enroll a new key.

Session challenge POST `/sessions/challenge` `{deviceId}` -> `{challengeId,nonce,expiresAt}` (60s). POST `/sessions` `{deviceId,challengeId,signature}` -> `{session,expiresAt,authGeneration,hostId,deviceId,accountId}`. Signature Ed25519 over `UTF8("vesta.host.session.v1\0") || JCS({hostId,deviceId,challengeId,nonce,expiresAt})`. Consume challenge before signature verification; host/device bound, no replay. Key-possession and active device/account checks both required. No anonymous device enrollment. Unknown/revoked device same 401. Rate limits apply to known and unknown devices.

## PAKE profile (claim and link)

Choose asymmetric SPAKE2, Rust `spake2 = "=0.4.0"`, `Ed25519Group`, launcher side A, host side B; exchange the crate's exact 33-byte messages including side marker.
Implementation decision (2026-11-13): retain the exact stable 0.4.0 release (not 0.5 prereleases), shared by the server and native Rust/Tauri launcher through `vesta-host-client`. The [RustCrypto upstream](https://github.com/RustCrypto/PAKEs) still maintains this crate (including 0.5 prerelease development); [published 0.4.0 package](https://docs.rs/crate/spake2/0.4.0) resolves and builds on our Windows Rust toolchain. This establishes availability and shared native compatibility, not an independent security audit. No browser PAKE implementation or handwritten primitive is permitted.

It provides a small Rust pairing primitive with explicit identities; add exporter binding and mutual confirmation below. This is the crate's wire profile, not a claim of RFC 9382 interoperability; [crate documentation](https://docs.rs/spake2/0.4.0/spake2/) warns of no independent audit and timing limitations, so review and cross-client vectors are a release gate.

Code: 12 cryptographically random Crockford base32 characters (60 bits), display `XXXX-XXXX-XXXX`; strip ASCII hyphens/spaces, uppercase ASCII, reject characters outside `0123456789ABCDEFGHJKMNPQRSTVWXYZ`. Password is canonical ASCII code. Setup code expires at 30min, exists only while unclaimed; local `vesta setup-code` rotates it and cancels all older claim exchanges. Link code expires at 10min. V1 permits one active link code per host; creating another invalidates the previous code and exchanges, so code-only entry can select it without sending the password. Raw code kept only in host-private state/memory until expiry/use; never log or send code over HTTP. Hash-only storage is insufficient for balanced SPAKE2. Delete after claim/link; store consumed exchange results separately for retry.

1. TLS 1.3 dedicated connection, no 0-RTT/resumption during bootstrap. Client initially permits an untrusted self-signed certificate only on this restricted connection. It MUST NOT send account tokens, ordinary host credentials, browsing or management requests until PAKE authenticates the peer. Native launcher transport must expose TLS exporter; a WebView fetch cannot implement this profile.
2. POST `/pake/start` `{purpose:"claim"|"link",linkId:null|UUID,hostId,deviceKey,clientNonce,messageA}` -> `{exchangeId,hostId,fingerprint,serverNonce,messageB,expiresAt}`. `deviceKey` 32 bytes Ed25519, nonces 32 random bytes. For claim linkId is null; for link use id from link-code entry (a typed code is resolved locally by the host's one active local link code when linkId is null). Request hostId must equal host identity learned from discovery. Exchange lifetime 120s, in memory and pinned to that TLS connection; start consumes a rate-limit attempt. SPAKE identities `UTF8("vesta.host.pake.v1/A\0"+purpose+"\0"+hostId+"\0"+deviceKey)` and B same with `/B`.
3. Define `T=JCS({v:1,purpose,linkId,hostId,fingerprint,deviceKey,clientNonce,serverNonce,exchangeId,messageA,messageB,expiresAt})`, with the effective returned linkId for link (host includes it in start response). `E=TLS-Exporter("EXPORTER-Vesta-host-pake-v1",empty_context,32)`. `K=HKDF-SHA256(ikm=SPAKE2.finish(peerMessage),salt=E,info=UTF8("vesta.host.pake.key.v1\0")||SHA256(T),L=32)`.
The empty exporter context is intentional: capture E once from the completed handshake before handing the stream to HTTP. HKDF info and both confirmations bind SHA256(T), including both PAKE messages and the accepted certificate fingerprint. Use the accepted TLS snapshot fingerprint, never a later listener reload. This replaces the draft transcript-dependent exporter call, without dropping transcript or connection binding.

4. POST `/pake/finish` `{exchangeId,clientConfirm}` on same connection; confirmation is HMAC-SHA256(K, UTF8("client\0")||SHA256(T)). Host constant-time verifies, replies `{serverConfirm,pakeToken,expiresAt}` with HMAC over `"server\0"||SHA256(T)`. Both verify before proceeding. `pakeToken` random 32 bytes, valid 10min on this connection and device key/purpose only, gives only account-proof+claim/link completion authority. Use `Authorization: Pake <pakeToken>` there; ordinary Bearer is not accepted instead. Code is consumed atomically on final enrollment, not merely finish (otherwise account outage loses setup). Disconnect destroys capability; retry PAKE while code remains valid. Rotating code invalidates all capabilities derived from it.

At most 16 outstanding exchanges/host, two/IP, starts 5/min/IP and 20/min/host with bounded IP buckets, global backoff after repeated failures, fail closed at capacity. Finish only once; wrong code/proof, expired/unknown link/code, already-claimed claim start give uniform 401 `pairing_failed`, with equivalent bounded work. Do not expose error distinctions to unknown peers. Invalid finish cannot consume a valid setup code. Rotations/approval/claim are audited without codes, PAKE messages or confirmations. LAN discovery's state is the explicit privacy exception.

## Microsoft-backed account verification

Reuse `identity/minecraft/{challenge,provider}.rs`, not a new bearer-token verifier. The launcher signs in with Microsoft and obtains its Minecraft Services access token through its existing account flow. That token's audience is Minecraft Services; it stays in the launcher, which uses it ONLY at `https://sessionserver.mojang.com/session/minecraft/join`. Host accepts **no** Microsoft, Xbox, Minecraft access token or client JWT as identity proof; therefore no client-supplied JWT issuer/audience is trusted. Host trusts only a fixed HTTPS Mojang session-service response using WebPKI, redirects/proxies disabled, bounded body and provider concurrency as in today's adapter.

POST `/accounts/challenge` `{accountId,name,deviceKey,purpose:"claim"|"link"|"invite"|"signin",binding}`. For claim/link use PAKE authorization, binding is exchangeId and deviceKey must match PAKE; invite authorization is its code capability and binding is SHA256(JCS(invite payload)), with key possession checked at completion; signin has no Authorization header and binding is the connection's TLS certificate fingerprint (see account sign-in below). Return `{challengeId,serverHash,nonce,expiresAt}` with 60s TTL; `nonce` is the base64url nonce inside serverHash. Record hostId, deviceKey, PAKE exchange/invite, requested UUID/name, purpose and nonce. Generate `serverHash=lowerhex(SHA256(UTF8("vesta.host.account.v1\0")||JCS({hostId,deviceKey,purpose,binding,accountId,nonce}))[0..20])` (40 hex characters); nonce 32 random bytes. This is a fresh random Minecraft serverId, not a Minecraft game's SHA-1 digest.

Launcher POSTs Mojang join `{accessToken:<Minecraft token>,selectedProfile:<compact UUID>,serverId:<serverHash>}`; never sends token to Vesta. Then POST `/accounts/complete` `{challengeId,signature}`; signature over `"vesta.host.account.v1\0" || JCS({hostId,deviceKey,challengeId,serverHash,purpose,binding})`. Host consumes challenge before external I/O, checks same capability/key/purpose, queries fixed `hasJoined?username=<name>&serverId=<serverHash>`, checks returned UUID exactly and name case-insensitively, then returns `{accountProofId,accountId,expiresAt}`. Proof expires 120s, single-use, connection/device/purpose-bound. Returned display name is informational. Invalid provider result 401, unavailable provider 503. Fresh verification cannot attach an existing key to a different account.

Claim POST `/claim` `{exchangeId,accountProofId,deviceName,signature}`, with Pake authorization. Signature over `"vesta.host.claim.v1\0" || JCS({hostId,exchangeId,accountProofId,deviceKey,deviceName})`. One DB transaction checks unclaimed, current code epoch, unexpired PAKE/proof, installs primary account and device, consumes code/proof, advances generation and writes audit. Return `{hostId,fingerprint,accountId,deviceId,session,expiresAt,authGeneration}`. Only now persist TLS pin and credentials. A concurrent claimant fails uniformly. Lost response: an exact claim retry on the original live PAKE connection returns the committed account/device and a fresh session. The consumed PAKE token authorizes only that exact durable receipt until its original expiry or disconnect; it cannot verify another account or enroll again. After reconnect, redo device session proof over the PAKE-proven pin; no second owner creation. If the device id was lost with the reply, POST `/sessions/challenge` with `{deviceKey}` instead of `{deviceId}` returns `{deviceId,challengeId,nonce,expiresAt}`. The host resolves only an active key; unknown/revoked keys receive the same shape with a random device id and fail completion uniformly. This lookup grants no authority: the fresh session signature is still mandatory. Do not accept claim based solely on an existing server Owner session as today's onboarding does.

## Account sign-in on a new device

Implementation decision (2026-11-13): permissions follow the verified Minecraft account, not a per-device code. On a claimed host, a new device that (a) pins the host's TLS identity, (b) proves possession of its new Ed25519 device key and (c) completes a fresh Mojang-backed account proof bound to hostId, certificate fingerprint, device key and purpose `signin` is enrolled as a device of that account with no link code and no owner approval, provided the account already holds a role here (primary owner, owner, or a grant on any non-deleted server). It then receives a normal host session. Link codes remain an optional fallback (below).

**Trust on first connect.** There is no setup code, so no PAKE proves the certificate. The launcher pins `(hostId, fingerprint)` from exactly one of: (a) an invite or link it holds (out-of-band fingerprint); (b) a machine it already knows on another launcher profile (existing pin); (c) trust-on-first-use of the certificate presented at the address the user typed or picked from discovery, shown to the user as the machine name before any account step. Discovery/mDNS data never overrides an existing pin; a later certificate mismatch for a pinned hostId is a hard "machine identity changed" error, never a silent re-pin. The pinned fingerprint is the SHA-256 of the leaf certificate the launcher observed on its own TLS connection, never a value read from a response body.

**Binding.** For `purpose:"signin"` the binding is that observed fingerprint (64 lowercase hex). The host refuses a challenge whose binding differs from the accepted TLS snapshot fingerprint of the connection it arrived on, and records the challenge, proof and enrollment against that connection; completion or enrollment on another connection fails. serverHash covers `{hostId,deviceKey,purpose,binding,accountId,nonce}`, so the only account-authenticated artifact, the Mojang join, names this hostId, this certificate and this device key. Before calling Mojang join the launcher MUST recompute `serverHash` with `vesta_host_client::requests::account_server_hash` from its pinned hostId, observed fingerprint, its own device key, the accountId it is signing in and the returned `nonce`, and MUST abort on mismatch. The completion signature additionally covers hostId and the fingerprint (as binding), and the enrollment signature `Sign("vesta.host.signin.v1\0" || JCS({hostId,fingerprint,accountProofId,deviceKey,deviceName}))` covers both again.

**First-connect man-in-the-middle.** In case (c) an attacker who intercepts the first connection can impersonate the machine to that launcher: show a fake name and server list, receive anything the user then sends to the fake machine (console input, uploaded files) and offer content the user might install. It learns the user's public Minecraft UUID/name and the device public key. It cannot: obtain a session, device or any grant on the real host; reuse the account proof there; or learn a password or token (Vesta never receives the Minecraft access token). Relaying the real host's challenge to the launcher fails the launcher's serverHash check because that hash names the real certificate (and the attacker's device key, if it substituted its own), so the launcher never performs a Mojang join the real host would accept. A join the launcher does perform names the attacker's certificate, which the real host rejects at challenge (binding) and at completion (hasJoined uses the real host's own serverHash). The device signatures name the attacker's fingerprint and fail at the real host. Once the user later reaches the real host, the pin mismatch exposes the interception. Cases (a) and (b) leave no first-use window. Launchers MUST generate a separate device key per host so that a device signature for one host is never useful at another.

**Policy.** Account with no role (unknown, disabled, or holding no owner/server role) gets 403 `account_has_no_access`, uniform for those cases, after the proof is verified; no device or account record is created and the proof is consumed. Host setting `newDeviceSignIn:"account"|"approval"` (default `"account"`, owner-editable via PATCH `/v1/host`, audited): in `"approval"` mode a new key gets 403 `device_approval_required`, nothing is created, and the device must use the link-code flow with owner approval. Every automatic enrollment advances authGeneration, writes audit action `device_sign_in` (actor accountId, target deviceId) and appears in GET `/v1/host/devices` with its created time and client-supplied name; DELETE `/v1/host/devices/{id}` revokes it as any other device (generation bump, sessions end). Revoking a device does not remove the account's role: that account may sign in again with a new key and fresh proof; remove its owner/server role to cut it off. A revoked key can never re-enroll (409 `device_key_unusable`). A key already active for the same account returns that device with a fresh session (lost-reply retry); a key enrolled for another account gets 409 `device_key_unusable`. Primary-owner protections are unchanged; sign-in never grants a role. Device name: client-supplied, at most 256 input bytes; control, zero-width and bidi-override characters removed, whitespace collapsed, trimmed, truncated to 64 characters, empty becomes a refusal. The stored name is returned in the enrollment response, device lists and link status.

Sequence, one dedicated TLS 1.3 connection, no Authorization header until step 5:
1. Connect; record observed leaf fingerprint F. GET `/v1/host/discovery` -> `{hostId,fingerprint,...}`; require `fingerprint == F` and apply the trust rule above to `(hostId,F)`.
2. POST `/accounts/challenge` `{accountId,name,deviceKey,purpose:"signin",binding:F}` -> `{challengeId,serverHash,nonce,expiresAt}`. Anonymous challenges are limited to 5/min/address and 30/min/host (429 `rate_limited`).
3. Verify `serverHash == account_server_hash(hostId,deviceKey,"signin",F,accountId,nonce)`; then Mojang join with that serverHash.
4. POST `/accounts/complete` `{challengeId,signature}` (signature over `"vesta.host.account.v1\0" || JCS({hostId,deviceKey,challengeId,serverHash,purpose:"signin",binding:F})`) -> `{accountProofId,accountId,expiresAt}`.
5. POST `/sign-in` `{accountProofId,deviceKey,deviceName,signature}` -> 200 `{state:"enrolled",hostId,fingerprint,accountId,deviceId,deviceName,session,expiresAt,authGeneration}`; or 403 `account_has_no_access` / `device_approval_required`, 409 `device_key_unusable`, 401 `pairing_failed` (bad, expired, reused or foreign proof/signature), 503 `account_verification_unavailable`. Persist pin, hostId, deviceId and key on success. A lost reply is recovered with POST `/sessions/challenge` `{deviceKey}` and a fresh session signature.

## Device link

Optional path, kept for a host whose owner chose `newDeviceSignIn:"approval"` or a person who prefers a code. Owner creates link code; new device runs link PAKE and account proof. Link device names must already be in the sanitised form above. POST `/links` with Pake authorization `{exchangeId,accountProofId,request,signature}`, request `{hostId,linkId,deviceKey,accountId,requestedRole:"linked_device",deviceName,nonce,expiresAt}`. Nonce 32 random bytes, expiry <=120s. Sign `"vesta.host.link.v1\0" || JCS(request)`. Host checks exact verified UUID and code's target account, consumes proof, returns `{linkId,state:"awaiting_approval",requestHash}`. Linking never grants owner or server role by request: authority follows existing verified account grants. Supporting a brand-new account without grants is harmless but shows no servers.

GET `/links/{linkId}` -> `{state,requestHash,deviceName,accountId,expiresAt}` under Pake or Owner authorization; only owner response includes the original signed request. Owner sees verified account and device; POST `/links/{linkId}/approve` `{requestHash}` commits exact request (no key/account substitution), consumes code, creates device and increments generation. Local `vesta link --approve` uses the privileged channel with same hash. New device polls (<=1/s) and on approval receives `{state:"approved",deviceId}` then establishes a normal device session. Pending link expires with code, cannot survive code rotation; approval after expiry/revocation fails. No owner available means local privileged approval, never automatic code-only linking. New device obtains a session only after approval. On approval the consumed link PAKE token retains read-only access to that exact link result on the same live connection until token expiry, code rotation or disconnect; it cannot authorize account proof, another enrollment, or ordinary management. After reconnect or a lost approval reply, the device-key session challenge above recovers the enrolled device id.

Invites use fresh account proof and the same device-key possession signature, prefix `vesta.host.invite.v1\0` over JCS({hostId,serverId,inviteHash,accountProofId,deviceKey}); no PAKE needed for a 256-bit invite code. Code authorization `Authorization: Invite <code>` allows only its account challenge/complete and redemption. Resolve invite code before using its endpoints or pack metadata as authority; anonymous misses are uniform.

Certificate rotation is separate: new leaf fingerprint is signed by the old TLS identity key with hostId and monotonic rotation revision; linked devices require old-pin proof or local re-link. Discovery alone never updates a pin. Exact rotation wire profile is deferred; v1 acceptance does not expose remote rotation.

### Server invite account proof

Without PAKE, the account challenge/complete routes also accept purpose `invite`. The binding is lowercase SHA-256 hex of the decoded canonical invite payload. The proof remains bound to the live TLS connection and the device key, and is consumed atomically with invite usage, enrollment and the server grant. The redeem signature uses `vesta.host.invite.v1\0` and JCS({hostId,serverId,inviteHash,accountProofId,deviceKey}); no access token is accepted. See README Server access.
